# Internationalisation

Two locales, both first-class. English is the default.

## URL shape

| Locale | Pathname |
|---|---|
| English | `/`, `/about`, `/blog/<slug>`, `/faq`, ... |
| Chinese | `/zh/`, `/zh/about`, `/zh/blog/<slug>`, `/zh/faq`, ... |

Controlled by `astro.config.mjs`:

```js
i18n: {
  defaultLocale: 'en',
  locales: ['en', 'zh'],
  routing: { prefixDefaultLocale: false },
}
```

`hreflang` links are emitted on every page's `<head>` pointing at both locales
plus an `x-default` fallback pointing at English.

## How the locale is detected at render time

`src/utils/i18n.ts` exposes helpers:

- `localeFromPath(pathname)` — returns `'en'` or `'zh'`
- `localisedUrl(path, locale)` — canonical path → locale-specific path
- `canonicalPath(pathname)` — strips `/zh` prefix
- `alternateLocaleUrl(pathname)` — switches locales for the language switcher
- `hreflangEntries(pathname)` — returns the three `<link rel="alternate">`
  entries for the head

The `<html lang>` attribute is set from `HTML_LANG[locale]` in
`src/i18n/strings.ts`. `en` maps to `en-CA`, `zh` maps to `zh-Hant`.

## UI chrome strings

`src/i18n/strings.ts` holds every recurring UI string — nav labels, footer
tagline, a11y text. Keys are the same in both locales; values are the
translated text. Example:

```ts
export const STRINGS = {
  en: {
    nav: { home: 'Home', about: 'About', ... },
    ...
  },
  zh: {
    nav: { home: '首頁', about: '關於', ... },
    ...
  },
};
```

If you add a string, add the translation immediately. No English-only fallback.

## Bilingual content on static pages

Home, About, What We Teach, and Privacy are visually bilingual: each section
has an English column and a Chinese column. The `/` and `/zh/` routes render
the **same** body component; the only per-locale differences are `<html lang>`,
header/footer chrome, and page metadata.

This works because the bilingual content lives in a single
`src/components/content/<Page>Content.astro` component. Each
`ApproachSection` (or `BilingualBlock`) accepts `<div slot="en">` and
`<div slot="zh">` children.

Inline `lang` attributes on each column tell screen readers and search engines
which language they're reading. Example:

```astro
<div class="approach__col approach__col--en" lang="en-CA">...</div>
<div class="approach__col approach__col--zh" lang="zh-Hant">...</div>
```

## Collection content (blog, FAQ, useful_words)

These are **monolingual per route**. `/blog` shows English entries; `/zh/blog`
shows Chinese entries. Translation pairing is tracked by the `pair_key`
frontmatter field.

To add a bilingual collection entry, see
[`content-authoring.md`](content-authoring.md). The short version: create two
markdown files, one under `.../en/`, one under `.../zh/`, with matching
`pair_key` and same-ish structure.

## The language switcher

`src/components/LangSwitch.astro` renders a single link that flips to the
alternate locale of the current path. Implementation is a pure link — no JS.

If the current path has no translation pair (e.g. a blog post that only
exists in one language), the switcher still flips to the other locale's base
path. We don't currently detect "no pair" and do a smarter redirect; the
assumption is that every committed post ships with both languages. If this
assumption breaks, see `alternateLocaleUrl` in `src/utils/i18n.ts` for the
place to add fallback logic.

## Typography per locale

`src/styles/tokens.css` declares two font stacks:

- `--font-display`: `'Literata', 'Noto Serif TC', ui-serif, ...`
- `--font-body`: `'Atkinson Hyperlegible Next', 'Noto Sans TC', system-ui, ...`

For English-primary pages, Literata and Atkinson lead. Browsers fall back to
Noto Serif TC / Noto Sans TC character by character when Latin fonts don't
have the glyph. That handles English sentences with inline Chinese.

For Chinese-primary pages (`html[lang^="zh"]`), the cascade swaps the order
so the Chinese fonts lead. Same fallback works in reverse.

Inline `[lang="zh-Hant"]` regions inside an English-primary page trigger the
same font swap locally.

## Adding a new locale (future)

Not supported today. If you do this:

1. Add the locale to `astro.config.mjs`'s `locales` array.
2. Add a `Locale` union entry in `src/i18n/strings.ts` and translate every
   string in `STRINGS`.
3. Add the locale to `HTML_LANG` and `LOCALE_DISPLAY`.
4. Add a `<Locale>Content` fall-through for each static page, or refactor to
   drive content from collections.
5. Add a font stack override in `tokens.css` if the new language needs
   different fonts.
6. Generate the new route tree under `src/pages/<locale>/`.
7. Update `alternateLocaleUrl` and `hreflangEntries` in `src/utils/i18n.ts`
   to handle the third locale (currently binary EN/ZH).

Expect the switcher UI to need redesign — a toggle doesn't scale past two
languages.
